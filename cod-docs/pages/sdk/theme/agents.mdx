# Use AI to build a theme

AI can write a theme quickly, but a theme has rules that are easy to guess
wrong. This page is written for both people in the conversation:

- **If you are the developer:** give this page to your assistant together with
  the theme manifest and the document you want changed. You still decide what
  the theme should look like.
- **If you are the assistant:** work from the manifest and the document
  operations. Never invent a field, a component type or an id.

The goal is not to stop the assistant from writing code. The goal is to keep it
inside the contract, so the page still renders for shoppers after every change.

## Give the assistant these three things

| Give it | Why |
| --- | --- |
| The theme manifest | It lists the real component types, fields, slots and surfaces |
| The target document or surface | It says what page is being changed |
| The result you want, in plain words | It replaces guessing from a screenshot |

If the assistant changes a definition, also give it the validation command or
test command the theme uses.

## Read these first

| If you need to… | Read |
| --- | --- |
| Know which fields exist | `manifest.components[type].fields` |
| Know which slots and blocks exist | `manifest.components[type].slots`, `fixed`, `placement` |
| Know which surfaces and areas exist | `manifest.surfaces`, `manifest.areas` |
| Know the store's settings | `manifest.settings` |
| Change a document | [Manifest and editing](/sdk/theme/manifest) |
| Understand a refusal | `DocumentIssue.code` and `PageDataIssue.code` |

The manifest is generated from the live theme. Do not infer a field from a
component's markup, a screenshot or an older README.

## Invariants

These are the rules the assistant must follow. A developer does not need to
memorize them, but they explain why some changes are refused.

1. **Definitions are code; documents are data.** Never put functions, class
   instances or undefined values into a document.
2. **`type` is identity.** Do not rename it. Saved instances reference it.
3. **A component key equals its `type`.** `components["best-sellers"]` must
   hold a definition whose `type` is `"best-sellers"`.
4. **`id` is unique in the document.** Use `newInstanceId()`, or keep the id
   another tool already gave the instance; do not invent one that may collide.
5. **Defaults are materialized only at creation.** `createInstance` fills
   defaults; a later reader also falls back through content and defaults.
6. **`load` output wins over field props.** If a field and a `load` result use
   the same key, the loaded value wins.
7. **Hidden means not rendered, not removed.** It stays in the document, and a
   required block cannot be hidden away.
8. **Required and fixed blocks are guaranteed.** `completePage` adds them when
   a document lacks them.
9. **Images are media keys, not URLs.** An `image` value is a
   `MediaReference`; resolve it at render.
10. **No CSS in documents.** `style` values are steps and choices;
    `colorScheme` values are scheme ids.
11. **A saved document is untrusted.** Validate on read and degrade with
    reports; never throw the page away for one bad section.
12. **Theme code reads; the platform writes.** Do not add endpoints that save
    page documents, settings or merchant text. The theme receives saved data.

## Change protocol

1. **Locate the surface.** `home`, `product`, `collection`, `category`,
   `catalog`, `page`, or an area such as `area:header`.
2. **Open the document.** `resolveSurfaceDocument(theme, surface, saved)` gives
   the document that will render, already completed. If you are editing, start
   from `completePage(theme, page).page`.
3. **Choose the component.** Use a type in the manifest whose `placement` and
   `capabilities.surfaces` allow this location.
4. **Create the instance.**
   ```ts
   import { createInstance, manifestCatalog, newInstanceId } from "@wocart/theme";
   const definition = manifestCatalog(manifest).components["best-sellers"];
   const instance = createInstance(definition!, newInstanceId(), { limit: 4 });
   ```
   `limit` is a field of this example's `best-sellers` definition. In a real
   theme, pass only keys the manifest declares. `createInstance` throws on
   unknown keys, wrong types and a required field with nothing to fill it.
5. **Apply the change.** Use `insertInstance`, `moveInstance`,
   `duplicateInstance`, `setInstanceProps`, `setInstanceHidden` or
   `removeInstance`. They return `{ ok: true, page }` or
   `{ ok: false, issue }`.
6. **Check the whole document.** `checkPageData(theme, page)` returns every
   issue before saving.
7. **Validate the theme** after changing a definition:
   `validateThemeDefinition(theme)`.
8. **Preview and test.** Render the page, or use the preview route and the
   bridge; run the theme's contract tests.

## APIs to use

| Goal | API |
| --- | --- |
| Serialize a theme | `themeManifest(theme)` |
| Turn a manifest into an editable catalog | `manifestCatalog(manifest)` |
| Validate document shape and field values | `validatePageData(theme, input, scope)` |
| Strict writer check | `checkPageData(theme, page)` |
| Add required and fixed blocks | `completePage(theme, page)` |
| Choose the document that renders | `resolveSurfaceDocument(theme, surface, saved, scope)` |
| Make a new instance | `createInstance(definition, id, props)` |
| Generate an id | `newInstanceId()` |
| Edit a document | `insertInstance`, `moveInstance`, `duplicateInstance`, `setInstanceProps`, `setInstanceHidden`, `removeInstance` |
| Compare two releases | `diffThemeManifests(previous, next)` |

`manifestCatalog(manifest)` creates a `ThemeDefinition` with
`component: null`. It is for editing and validation only; do not render it.

## Refusals to handle

| Code | Meaning |
| --- | --- |
| `unknown-type` | The type is not in this catalog; nothing renders |
| `unknown-prop` | The prop is not declared; it is ignored |
| `invalid-prop` | The value fails the field rules; defaults are used |
| `missing-required-prop` | A required field has no value, content or default |
| `unknown-slot` / `disallowed-child` | The saved child no longer fits the slot |
| `duplicate-id` | A later instance repeats an id; the first wins |
| `limit-exceeded` | A slot, surface or depth limit was crossed |
| `theme-mismatch` | The document was composed for another theme |
| `not-available` / `not-placeable` | The component is not offered on this surface or location |
| `slot-full` / `required-block` / `fixed-block` | The operation would break composition rules |
| `load-failed` | A `load` threw; the base props still render |
| `missing-component` | A definition has no usable component reference |
| `multiple-slots-unsupported` | The reference renderer can fill one named slot per instance |

A page-level failure is different from a section-level one. Only an invalid
envelope (`version`, `surface` or `sections` shape) makes `page` null; every
other issue is a degradation with a report.

## Definition of done

- [ ] `validateThemeDefinition(theme)` returns an empty list.
- [ ] `themeManifest` survives a JSON round trip and validates.
- [ ] Every shipped document passes `validatePageData`.
- [ ] The changed page renders without unexpected `onIssue` reports.
- [ ] `diffThemeManifests` shows no accidental breaking change.
- [ ] The preview and a normal shopper render show the same content, minus the
      preview markers.
