# Fonctionnement

Une vitrine CodFlow comporte trois couches :

1. **Vos pages Astro** possèdent les routes, la mise en page, les textes et l'interaction.
2. **`@wocart/storefront`** lit la boutique et appelle son serveur. L'entrée racine
   est sûre pour le navigateur ; le client et la clé vivent sur le serveur.
3. **`cod-server`** possède les prix, le stock, les coupons, la livraison, l'OTP,
   l'acceptation des commandes et toutes les autres règles.

Conséquence importante : une page affiche ce que le serveur a renvoyé. Elle ne
calcule pas un prix, ne décide pas qu'un coupon s'applique et ne marque pas une
commande comme acceptée.

## Ce qu'un fichier source importe

| Votre fichier | Importer depuis |
| --- | --- |
| Frontmatter de page, middleware, action, route API | `@wocart/storefront/server` et `@wocart/storefront/astro` |
| Script navigateur ou island | `@wocart/storefront` |
| Script photo ou vocal d'avis | `@wocart/storefront/review-media` |

L'entrée racine n'a ni clé API ni fabrique de client. C'est délibéré, pas une
convention : le test de contrat du paquet échoue si l'implémentation de la clé
fuit dans l'artefact racine.

## Un client par requête

Créez le client là où la requête est servie, passez-le à la page et laissez-le
partir avec la réponse.

```ts
// src/theme/store.ts — server only
import { createStoreClient } from "@wocart/storefront/server";

export function getStore(locale?: string) {
  return createStoreClient({
    serverUrl: process.env.COD_SERVER_URL!,
    apiKey: process.env.STORE_API_KEY!,
    ...(locale ? { locale } : {}),
    onError: (error) => console.warn(error.operation, error.code),
  });
}
```

Un client détient la clé d'une boutique et les caches d'une langue. Ne le gardez
pas comme variable globale de module et ne le partagez pas entre boutiques.

## Types de pages et chemins

La plateforme possède ces chemins. Une vitrine affiche chaque page qu'elle prend
en charge au chemin utilisé par la plateforme, et construit ses liens avec
`storefrontPath`.

| Type de page | Chemin | Lectures principales |
| --- | --- | --- |
| Accueil | `/` | `config.get`, `products.list`, `collections.get` |
| Catalogue | `/products` | `products.page` |
| Catégorie | `/category/:slug` | `categories.list`, `products.list({ categoryId })` |
| Collection | `/collections/:handle` | `collections.get`, `products.list({ collection })` |
| Produit | `/products/:handle` | `products.get` |
| Page de boutique | `/pages/:slug` | `pages.get` |
| Page d'atterrissage | `/lp/:slug` | `pages.landing` |
| Commande | `/checkout` | Panier navigateur, puis `cart.validate` |
| Remerciement | `/thank-you` | `orders.tracking` |

```ts
import { storefrontPath } from "@wocart/storefront";

storefrontPath("product", { handle: "linen-shirt" });
storefrontPath("category", { slug: "women" });
storefrontPath("checkout");
```

Les autres chemins (`/about`, `/offers/summer`) appartiennent à votre projet
Astro. Le SDK ne les contraint pas.

## Une lecture se dégrade ; elle ne lève pas d'erreur

Chaque lecture se résout en une valeur vide lorsque le serveur est injoignable,
qu'une réponse ne correspond plus au contrat ou que la ressource n'est pas
publique :

| Lecture | Valeur vide |
| --- | --- |
| `config.get()` | `null` |
| `products.get()` | `null` |
| `products.list()` | `[]` |
| `products.page()` | `{ items: [], hasNext: false }` |
| `categories.list()` | `[]` |
| `collections.get()` | `null` |
| `menus.get()` | `null` |
| `pages.get()` / `pages.landing()` | `null` |
| `shipping.rates()` | `{}` |
| `geo.communes()` | `[]` |
| `cart.validate()` | un résultat d'échec |
| `orders.tracking()` | `null` |

Une décision de conception en découle : l'état vide fait partie de la page, pas
d'un gestionnaire d'exception. « Aucun produit pour l'instant » et « l'API est
brièvement indisponible » se ressemblent pour le lecteur. `onError` permet à
l'exploitant de les distinguer.

```ts
const products = await getStore().products.list();

if (products.length === 0) {
  return renderEmptyCatalog();
}
```

Un catalogue peut aussi être vide par conception. N'affichez pas de bandeau
d'erreur rouge sur une nouvelle boutique sans produits.

<Callout type="info" title="Null sur une page de détail est un vrai 404">
Pour `products.get`, `collections.get`, `menus.get`, `pages.get` et
`pages.landing`, `null` signifie « non public ou introuvable ». Affichez votre
404, pas une page 200 avec des champs vides.
</Callout>

## Une écriture renvoie un résultat

Les écritures ne lèvent jamais d'erreur en cas de refus. Elles répondent avec un
résultat discriminé :

```ts
const result = await store.orders.create(body);

if (!result.success) {
  if (result.domainError.category === "validation") {
    // Show the field issues.
  } else if (result.domainError.category === "business") {
    // Show the store's refusal.
  }
  return;
}

console.log(result.data.orderNumber);
```

`result.domainError` existe toujours en cas d'échec du SDK. Lisez sa `category`,
son `code`, `retryable`, `sideEffect` et `fieldIssues` plutôt que d'analyser un
statut HTTP.

Les catégories sont :

| Catégorie | Signification | Réponse habituelle |
| --- | --- | --- |
| `validation` | Un champ ou une forme est incorrect | Marquer le champ et conserver le formulaire |
| `authentication` | La clé de boutique ou la configuration est incorrecte | Journaliser ; ne pas réessayer dans le navigateur |
| `business` | La boutique a refusé la requête | Afficher le message du serveur |
| `transport` | Réseau, délai d'attente ou annulation | Proposer une nouvelle tentative quand `retryable` |
| `system` | Le serveur a échoué | Conserver la saisie de l'acheteur et proposer une nouvelle tentative |
| `unknown` | Une défaillance de passerelle non classée | Conserver la saisie ; ne pas annoncer un succès |

## Nouvelles tentatives et cache

Le SDK applique déjà la politique sûre :

- **Les lectures sûres** sont réessayées après un échec de transport ou un 5xx.
- **Les écritures ne sont jamais réessayées.** Une connexion coupée après une
  commande peut signifier que la commande existe. Vérifiez avant de demander à
  l'acheteur de soumettre à nouveau.
- `config.get()`, `categories.list()` et `geo.communes(id)` mettent en cache un
  résultat réussi pour la durée de vie du client. Les échecs ne sont jamais mis
  en cache.
- Les produits, pages, menus, collections, tarifs et données de page sont
  récupérés à neuf. C'est le cache de votre route qui décide de la fréquence de
  reconstruction d'une page.

`readTimeoutMs` vaut 10 secondes par défaut pour les lectures. Les écritures n'ont
pas de délai d'attente par défaut : une écriture interrompue par un minuteur a
peut-être déjà eu lieu.

## La frontière de sécurité

La clé de boutique est un secret serveur. Le code navigateur ne la voit jamais.

```text
Browser
  └─ POST /api/cart/validate        (your same-origin route)
       └─ createStoreClient(...)     (server only, key from env)
            └─ cod-server            (prices and rules)
```

C'est aussi pourquoi les assistants navigateur du SDK ne sont pas une seconde
API. `formatMoney`, le panier, la machine OTP et les constructeurs d'URL d'image
s'exécutent localement ; tout ce qui a besoin de la clé passe par votre route.

## Ce que le serveur décide encore

Même si votre page l'affiche, le serveur revérifie :

- le prix de chaque ligne du panier ;
- le stock et la vendabilité ;
- si un coupon s'applique ;
- les frais de livraison pour la destination choisie ;
- si OTP ou Turnstile est requis ;
- si une commande est acceptée ou non.

Le navigateur peut être optimiste. La commande ne l'est pas.
