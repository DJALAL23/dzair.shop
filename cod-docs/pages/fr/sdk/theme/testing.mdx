# Tester un thème

Un thème éditable fait quatre promesses : ses définitions sont valides, son
manifeste peut être enregistré et relu, ses pages par défaut passent la
validation, et ces pages sont rendues. Ces quatre vérifications prouvent ces
promesses dans votre propre suite de tests. Ajoutez des vérifications pour votre
propre comportement une fois qu'elles passent.

## 1. La définition du thème est valide

```ts
import { validateThemeDefinition } from "@wocart/theme";
import { theme } from "../theme/theme";

expect(validateThemeDefinition(theme)).toEqual([]);
```

Avec des packs de contenu déclarés, l'assemblage vérifie aussi chaque document par
défaut et chaque préréglage. Un tableau vide est la seule réussite.

## 2. Le manifeste se recharge proprement

```ts
import { themeManifest, validateThemeManifest } from "@wocart/theme";

const manifest = themeManifest(theme);
const checked = validateThemeManifest(JSON.parse(JSON.stringify(manifest)));

expect(checked.manifest).not.toBeNull();
expect(checked.issues).toEqual([]);
```

Ceci attrape une valeur non sérialisable, un désaccord clé/type et toute règle
relationnelle sur laquelle l'assemblage et la validation divergent. Une version
de thème non semver est le seul problème consultatif ; corrigez-la plutôt que de
l'autoriser.

## 3. Les pages par défaut sont valides

```ts
import { validatePageData } from "@wocart/theme";

for (const surface of theme.surfaces ?? []) {
  if (surface.document === undefined) continue;
  expect(
    validatePageData(theme, surface.document, {
      content: theme.content?.["fr"],
      locales: ["fr"],
    }),
  ).toEqual([]);
}

for (const area of theme.areas ?? []) {
  expect(
    validatePageData(theme, area.document, {
      content: theme.content?.["fr"],
      locales: ["fr"],
    }),
  ).toEqual([]);
}
```

Exécutez-la pour chaque langue déclarée, pas seulement pour la principale. Une
valeur traduite que seule une langue résout peut cacher une clé de contenu
manquante.

## 4. Les pages par défaut sont rendues

Rendez chaque section via `InstanceView` avec le conteneur d'Astro, un cache de
lecture par page et un `StoreClient` de remplacement :

```ts
import { experimental_AstroContainer as AstroContainer } from "astro/container";
import { createReadCache, type RendererIssue } from "@wocart/theme/astro";
import InstanceView from "@wocart/theme/astro/InstanceView.astro";
import type { ThemeRenderContext } from "@wocart/theme";
import type { StoreClient } from "@wocart/storefront/server";
import type { StoreConfig } from "@wocart/storefront";

const container = await AstroContainer.create();
const issues: RendererIssue[] = [];
const page = theme.surfaces?.find((surface) => surface.key === "home")?.document;
if (page === undefined) throw new Error("the home surface ships no document");

const products: unknown[] = [];
const storefront = {
  products: { list: async () => products },
} as unknown as StoreClient;

const context = {
  store: {} as StoreConfig,
  content: {},
  locale: "en",
  isRTL: false,
  url: "/",
} satisfies ThemeRenderContext;

const reads = createReadCache();

for (const section of page.sections) {
  await container.renderToString(InstanceView, {
    props: {
      instance: section,
      theme,
      context,
      storefront,
      reads,
      onIssue: (issue) => issues.push(issue),
    },
  });
}

expect(issues).toEqual([]);
```

Un cache par rendu de page est l'essentiel : les sections sœurs partagent une
ressource, et des pages distinctes non. Vérifiez `issues` plutôt que
l'absence d'exception — le moteur de rendu se dégrade, il ne lève pas d'exception.

Un `load` n'est appelé que lorsque sa section est rendue. Donnez au client de
remplacement les méthodes que le load utilise, et faites-le échouer exprès dans un
test séparé :

```ts
const failingIssues: RendererIssue[] = [];
const failing = {
  products: { list: async () => { throw new Error("offline"); } },
} as unknown as StoreClient;

await container.renderToString(InstanceView, {
  props: {
    instance: page.sections.find((section) => section.type === "best-sellers")!,
    theme,
    context,
    storefront: failing,
    reads,
    onIssue: (issue) => failingIssues.push(issue),
  },
});

expect(failingIssues).toContainEqual(
  expect.objectContaining({ code: "load-failed" }),
);
```

Les props de base de la section sont tout de même rendues ; seule la partie
chargée manque.

## Tests de documents enregistrés

Les quatre vérifications couvrent les documents propres au thème. Ajoutez des
tests pour les documents qui viennent d'une boutique :

```ts
import { resolveSurfaceDocument } from "@wocart/theme";

const saved = {
  version: 1,
  surface: "home",
  sections: [
    { id: "gone-1", type: "removed-layout" },
    { id: "hero-1", type: "hero", props: { title: "Bonjour" } },
  ],
};

const result = resolveSurfaceDocument(theme, "home", saved, { locales: ["fr"] });

expect(result.page.sections).toHaveLength(1);
expect(result.issues).toContainEqual(
  expect.objectContaining({ code: "unknown-type", path: "sections[0].type" }),
);
```

| Cas à couvrir | Attendu |
| --- | --- |
| Aucun document enregistré | La valeur par défaut livrée |
| Enveloppe invalide | La valeur par défaut livrée, avec `page: null` de `parsePageData` |
| Document pour un autre thème | La valeur par défaut livrée, `theme-mismatch` |
| Type de section inconnu | Cette section disparue, le reste rendu |
| `sections` vide | Page vide — le marchand l'a vidée |
| Bloc requis masqué | Réaffiché par `completePage` |
| Liste au-delà de son `max` | Rendue jusqu'à `max`, `limit-exceeded` |

## Vérifications de publication

Avant une publication, comparez les manifestes :

```ts
import { diffThemeManifests } from "@wocart/theme";

const { breaking, additive } = diffThemeManifests(previous, next);
expect(breaking).toEqual([]);
```

Si un changement incompatible est intentionnel, augmentez la version majeure du
thème et dites ce qui se dégradera. Exécutez aussi
`pluralFormIssues(pack, locale)` sur chaque pack : elle signale une forme de
pluriel dont la langue a besoin mais que le pack omet, ou une forme que la langue
n'utilise jamais.

## Ce qu'il faut tester dans le navigateur

Les quatre vérifications n'exécutent pas de scripts navigateur. Testez
séparément :

- une section qui lie un comportement sur `PREVIEW_SECTION_LOAD_EVENT` se monte à
  nouveau après un patch ou un remplacement,
- un remplacement d'aperçu de page entière déclenche `astro:page-load`,
- les scripts du panier et de la commande continuent de fonctionner après une
  mise à jour d'aperçu,
- la page d'un client ne contient aucun commentaire `wocart:start` / `wocart:end`.

## Garder le moteur de rendu hors des tests navigateur

`@wocart/theme` et Zod sont des dépendances de serveur/build. Un script navigateur
peut importer les assistants sûrs pour le navigateur du SDK, mais jamais le moteur
de rendu ni les validateurs. Le `browser-bundle.test.ts` du SDK et le
`no-validator-in-browser.test.ts` du thème le gardent ; maintenez ces tests verts.

## Critères d'achèvement

- [ ] `validateThemeDefinition(theme)` est vide.
- [ ] L'aller-retour du manifeste valide.
- [ ] Chaque document par défaut valide dans chaque langue déclarée.
- [ ] Chaque document par défaut est rendu sans `onIssue` inattendu.
- [ ] Chaque repli de document enregistré a un test.
- [ ] `diffThemeManifests` ne signale aucun changement incompatible non voulu.
- [ ] Chaque pack passe `pluralFormIssues`.
- [ ] Le comportement navigateur a son propre test ou une vérification manuelle.
