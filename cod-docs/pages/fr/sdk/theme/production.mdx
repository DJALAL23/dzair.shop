# Production et mises à niveau

Un thème qui s'affiche n'est pas un thème livrable. Cette page est la liste qu'un
thème doit survivre avant qu'une boutique marchande en dépende : accessibilité,
droite-à-gauche, comportement responsive, états que personne ne dessine,
performance, sécurité, déploiement, et le chemin de mise à niveau entre versions
du SDK.

Rien ici ne change le contrat ; c'est la bonne façon de l'utiliser.

## Avant de livrer

| Domaine | À prouver |
| --- | --- |
| Contrat | `validateThemeDefinition(theme)` est vide ; le manifeste fait l'aller-retour ; chaque document livré valide dans chaque langue |
| Rendu | Chaque surface se rend sans `onIssue` inattendu |
| Langues | L'arabe se rend en RTL, le français et l'anglais en LTR, et aucune langue n'affiche la copie d'une autre |
| États | Données vides, absentes, invalides ou en échec : chacun rend quelque chose de sensé |
| Images | Chaque image a un `alt` (ou est volontairement décorative) et une `width`/`height` ou un ratio |
| Argent | Les totaux viennent du serveur ; le navigateur n'ajoute jamais de frais |
| Secrets | Aucune clé de boutique n'atteint un bundle navigateur |
| Build | `npx astro check`, `npm test` et `npm run build` passent |

## Accessibilité

Le SDK fournit les pièces ; le balisage est à vous.

- **Le texte alternatif est un champ, par langue.** La valeur d'un champ `image`
  est une `MediaReference` dont `alt` se résout dans la langue rendue ; passez
  `image.alt ?? ""` et laissez une image décorative avoir un alt vide plutôt
  qu'un nom de fichier.
- **Le texte riche rend du HTML échappé.** `richTextToHtml` échappe chaque nœud
  de texte et chaque attribut et écarte les liens dangereux, donc `set:html` est
  sûr — mais les niveaux de titre qu'il peut produire vont de `h2` à `h4`. Une
  page doit avoir exactement un `h1`, en général le champ titre de la section.
- **Le contraste se vérifie.** `contrastRatio(a, b)` donne le ratio WCAG ; 4,5
  est le plancher pour le texte courant, 3 pour le grand texte. Avertissez le
  marchand dans l'éditeur plutôt que d'accepter un schéma illisible.
- **Focus et clavier.** Chaque élément interactif est un vrai `<a>`, `<button>`
  ou contrôle de formulaire. Le SDK n'ajoute aucun gestionnaire de clic ; un
  `<div>` cliquable est votre bug, et il ne fonctionne pas au clavier.
- **Formulaires.** Les champs du formulaire de commande et leur validation
  viennent des réglages de la boutique ; étiquetez chaque champ avec le libellé
  du marchand, pas seulement un placeholder.
- **Mouvement.** Un bandeau défilant, un carrousel ou un compte à rebours doit
  respecter `prefers-reduced-motion`. Le SDK n'a aucune primitive d'animation et
  n'en ajoute pas.

## Droite à gauche

L'arabe est une langue de première classe ici, pas un ajustement de feuille de
style après coup.

- Mettez `dir={isRTL ? "rtl" : "ltr"}` et `lang={locale}` sur `<html>`, depuis le
  contexte de rendu. `StoreConfig.locales[].direction` est la réponse de la
  boutique pour chaque langue.
- Les classes de style du SDK utilisent des **propriétés logiques CSS**
  (`padding-inline`, `margin-block-start`), donc un champ `style` se miroite sans
  CSS supplémentaire. Écrivez votre CSS de la même façon :
  `margin-inline-start`, pas `margin-left`.
- Ne miroitez que ce qui porte une direction : chevrons, flèches « suivant »,
  progression. Ne miroitez pas un logo, un numéro de téléphone, une horloge ou
  une photo de produit.
- Les prix, les numéros de téléphone et les numéros de suivi restent LTR dans un
  texte RTL. Un numéro passe par `normalizeAlgerianPhone` vers le serveur, et le
  serveur le formate pour l'affichage.
- Testez avec la chaîne arabe la plus longue, pas la plus courte : la copie arabe
  est souvent plus longue que sa source anglaise, et un bouton à largeur fixe la
  coupe.

## Responsive

- **Les points de rupture sont ceux du SDK** : `base` partout, `md` à partir de
  768 px, `lg` à partir de 1024 px. Une valeur `style` est pensée mobile d'abord —
  un point plus large hérite du plus étroit, donc ne répétez jamais une valeur
  `base` dans `md`.
- **Les pas sont des pixels choisis par le thème.** `s4` vaut 16 px seulement
  parce que le thème l'a décidé ; un composant qui code `16px` en dur casse dès
  que le marchand choisit `s8`.
- **Images** : utilisez `productImageSource` du SDK storefront, ou les aides de
  domaine média avec `generateSrcSet`, pour qu'un téléphone ne télécharge pas une
  image de héros dimensionnée pour un ordinateur. `mediaImageService` fait la
  même chose pour `<Image>` d'Astro via le domaine média.
- **Le contenu décide de la hauteur.** Une section qui suppose deux lignes de
  titre casse en arabe ou avec un nom de produit long. Laissez le texte passer à
  la ligne ; utilisez `min-height`, pas `height`.

## Chaque état qu'une section rend

| État | Ce que l'acheteur doit voir |
| --- | --- |
| Données vides (`[]`, `null`, `{}`) | Un état vide, pas une mise en page cassée : pas de grille blanche, pas de « undefined » |
| Une lecture a échoué | Le même état vide ; l'exploitant voit la cause par `onError` du client |
| `load` a levé | Les props de base se rendent quand même ; le moteur signale `load-failed` |
| Le type est inconnu | Rien ne se rend pour cette instance ; le reste de la page survit (`unknown-type`) |
| Une prop est invalide | La valeur par défaut du champ s'applique et `invalid-prop` est signalé — jamais un crash |
| Un champ requis n'a pas de valeur | `missing-required-prop` ; le composant ne doit pas imprimer un titre vide |
| Rien n'est encore configuré | En aperçu seulement : un placeholder via `isPreview(blocks)`, pour que le marchand puisse sélectionner la section |
| Le document appartient à un autre thème | Le document livré par défaut se rend ; le marchand ne voit jamais une page vide |
| Le brouillon d'un éditeur est vide | Une page vide est une vraie réponse — le marchand l'a vidée |

<Callout type="caution" title="La dégradation est silencieuse pour l'acheteur, par conception">
Une vitrine ne doit pas lever parce que le catalogue est indisponible. Si une
page renvoie 500 sur une lecture échouée, cette lecture a été attendue sans
valeur de repli — `products.list()` renvoie déjà `[]`.
</Callout>

## Performance

- **Un cache de lecture par page.** `createReadCache()` partage une lecture entre
  les sections (et partage son rejet). Un cache par section multiplie la même
  requête par le nombre de sections ; un cache par processus fuit entre les
  visiteurs.
- **Un client par requête.** Le client storefront garde de petits caches optionnels
  (config, catégories, communes) par instance ; partager un client entre requêtes
  partage ces réponses entre acheteurs, langue comprise.
- **Gardez Zod hors du navigateur.** Rien dans la page d'un acheteur ne doit
  importer les validateurs du SDK thème ni un module de schéma. La validation se
  fait là où la donnée entre : dans une route, ou dans le build.
- **Prérendez ce qui ne dépend pas de la requête.** Le manifeste et le point
  d'entrée des styles sont des artefacts de build (`prerender = true`).
- **Les images pèsent lourd.** Redimensionnez sur le domaine média, envoyez un
  `srcset`, et donnez à chaque image des dimensions intrinsèques pour éviter les
  décalages de mise en page.
- **Une page composée est un budget.** Cinquante sections se rendent ; cela ne
  veut pas dire qu'elles le doivent. Chaque section est au moins une lecture et
  un arbre de composants.

## Sécurité

- La clé API vit dans un module serveur et une variable d'environnement serveur.
  Une clé `PUBLIC_*` est une clé publiée.
- Les champs `url` acceptent seulement chemins du site, fragments, requêtes,
  `http(s)://`, `mailto:` et `tel:` ; `javascript:`, `data:` et les cibles
  protocol-relative sont rejetés à l'assemblage et signalés à la lecture.
  Rendez-les dans un `href`, jamais en HTML brut.
- Le texte riche est un format fermé : aucun nœud HTML n'existe pour être stocké,
  et `richTextToHtml` échappe ce qu'il émet. Ne faites pas `set:html` sur un champ
  `text` ou `textarea` brut.
- Une valeur d'image est une **clé** média ; l'URL est dérivée au rendu. Un
  document enregistré ne peut pas pointer un `<img>` vers un autre hôte.
- Le thème **lit** ; la plateforme écrit. Aucun point d'entrée d'un thème
  n'enregistre un document, un réglage ou un texte marchand — c'est CodFlow
  Studio, et un thème qui en ajoute un a inventé une frontière d'autorisation
  qu'il ne peut pas appliquer.
- Les jetons d'aperçu sont signés par l'éditeur et vérifiés avec la clé d'aperçu
  du déploiement ; sans clé, le thème répond 404 sur la route d'aperçu. Ne cachez
  jamais une réponse d'aperçu.
- Le style inline se limite à la feuille des schémas de couleurs qu'écrit
  `ThemeStyles.astro` ; sur une page avec une Content-Security-Policy, il ajoute
  le hash de cette feuille, donc `style-src` n'a pas besoin de `'unsafe-inline'`.

## Déployer

1. **Choisissez un adaptateur.** Tout adaptateur serveur Astro convient. Theme-00
   livre à la fois l'adaptateur Cloudflare et Vercel ; le code de composition est
   identique.
2. **Définissez les secrets.** `COD_SERVER_URL` et `STORE_API_KEY` vont dans le
   coffre de secrets de l'hébergeur. `COD_SERVER_URL` doit être une origine
   publique joignable par le déploiement — une valeur loopback qui marche en
   local rend une boutique vide en production.
3. **Un build, toutes les boutiques.** Un build de thème n'est pas par boutique :
   la boutique se décide par requête, par la clé et la configuration. Si vous
   liez un domaine média, lisez-le par un getter (`() => MEDIA_DOMAIN`) pour que
   le build ne fige pas le domaine d'une boutique dans l'artefact.
4. **Sachez quelles pages sont statiques.** `wocart-theme.json`,
   `wocart-styles.css` et toute page écrite à la main sont prérendus ; une page de
   surface est rendue par requête. Une page prérendue ne peut pas lire
   `Astro.locals` — un build n'a pas de boutique.
5. **Cachez délibérément.** Si vous cachez une page rendue, taguez-la et retirez
   le tag sur `REVALIDATE_PATH` après une publication ; une réponse d'aperçu
   n'est jamais mise en cache.
6. **Vérifiez après le déploiement** : `/wocart-theme.json` se lit et valide, la
   feuille est servie en `text/css`, et une page produit se rend dans chaque
   langue publiée.

## Versions et mises à niveau

Les deux paquets suivent le versionnage sémantique : un patch corrige le
comportement, une mineure ajoute des fonctions rétrocompatibles, une majeure peut
retirer ou changer un export. Un export est marqué `@deprecated` pendant au moins
une version mineure avant qu'une majeure ne le retire.

| Fait | Valeur au moment de la rédaction | Pourquoi c'est important |
| --- | --- | --- |
| `@wocart/theme` | `2.1.0` | `THEME_SDK_VERSION` dans chaque manifeste |
| Peers de `@wocart/theme` | `@wocart/storefront ^1.14.0`, `astro ^7.0.0` (optionnel) | npm refuse une installation hors plage |
| `@wocart/storefront` | `1.19.0` | Son entrée racine est sûre côté navigateur ; `/server` ne l'est pas |
| Peer de `@wocart/storefront` | `zod ^4.4.3` | Ses schémas font partie de son API publique |
| Contrat du manifeste | `THEME_MANIFEST_CONTRACT_VERSION` = `1` | Un éditeur lit les manifestes de cette version |
| Protocole d'aperçu | `PREVIEW_PROTOCOL_VERSION` = `1` | L'éditeur et le bridge doivent s'accorder |

Épinglez des versions **exactes** dans un thème (`npm install --save-exact`). Un
thème est rendu par son propre déploiement : une plage flottante signifie
seulement que deux builds du même commit peuvent différer.

La liste de mise à niveau :

1. Lisez le `CHANGELOG.md` du paquet pour chaque version franchie, pas seulement
   la dernière.
2. Changez l'épingle, puis lancez `npx astro check`, `npm test` et
   `npm run build`.
3. Lancez le contrôle de publication — `diffThemeManifests(previous, next)` avec
   les manifestes des deux versions — et lisez chaque entrée marquée comme
   cassante.
4. Relancez `validateThemeDefinition` : un SDK plus récent peut vérifier plus que
   l'ancien (2.0 a ajouté la garantie du formulaire de commande et la réservation
   de `blocks`).
5. Relancez l'aperçu et un rendu acheteur, en arabe comme dans la langue
   principale.

Ce que 2.0 a changé, si vous venez de 1.x :

- Une surface `product` doit garantir un formulaire de commande, sinon
  l'assemblage échoue.
- `blocks` est un nom de prop réservé ; aucun champ ne peut l'utiliser.
- Le lecteur écarte ce qui dépasse `THEME_LIMITS` et signale `limit-exceeded`.
- Un éditeur en 1.x rejette un manifeste qui utilise `style`, `colorScheme`,
  `colorSchemes`, `productList` ou `collectionList`. Mettez à niveau le thème et
  l'éditeur ensemble.

## Erreurs courantes

| Erreur | Ce qu'elle coûte |
| --- | --- |
| Renommer `defineTheme({ key })` | Toutes les éditions de texte et tous les documents de page du thème sont orphelins |
| Renommer le `type` d'un composant | Les instances enregistrées cessent de se résoudre (`unknown-type`) |
| Réduire `slots[].allow` | Les enfants qui ne correspondent plus sont retirés des pages enregistrées (`disallowed-child`) |
| Changer l'`id` d'un document livré | L'édition du marchand reste attachée à l'ancien id |
| Une clé de champ qui entre en collision avec une clé de `load` | La valeur chargée gagne et le champ ne fait rien, silencieusement |
| Une faute dans un `contentKey` | Le champ retombe sur sa valeur par défaut ; rien n'échoue avant `validateThemeDefinition` avec `contentKeys` |
| Coder en dur une couleur, un pas d'espacement ou une police | Le choix `style` / `colorScheme` du marchand n'a aucun effet |
| Stocker une URL dans un champ `image` | L'image ne se résout jamais ; le champ attend une clé média |
| Lire `Astro.locals.store` dans une page prérendue | Erreur de build, ou page vide |
| Un cache de lecture par section | Le même produit est récupéré une fois par section |
| Une route de thème qui enregistre un document | Le thème n'a aucune autorité d'écriture ; CodFlow Studio la détient |
| Traiter les choix de Theme-00 comme le contrat | Ses catalogues par surface, sa mise en page de contenu et son design system sont des décisions de ce thème — voir [l'analyse de référence](/sdk/theme/reference-implementation) |
