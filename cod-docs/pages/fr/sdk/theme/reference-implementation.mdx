# Implémentation de référence : Theme-00

`cod-astro/theme-00` est la vitrine complète de CodFlow (Astro 7, Cloudflare et
Vercel, AR/FR/EN). C'est l'exemple concret sur lequel les SDK sont construits, et
le meilleur endroit pour voir les coutures réelles d'un thème.

C'est **une** implémentation correcte, pas **la** spécification. Cette page la
cartographie : ce qu'elle prend des SDK, ce qu'elle a décidé elle-même, et ce
qu'un nouveau thème doit copier ou laisser de côté.

<Callout type="caution" title="Le code fait foi, pas ce résumé">
Theme-00 évolue. Quand cette page et le thème divergent, lisez
`cod-astro/theme-00/AGENTS.md` et le fichier lui-même. Rien ici ne prime sur les
déclarations des paquets.
</Callout>

## Où il se situe

- **Pas un workspace.** Il installe `@wocart/storefront` et `@wocart/theme`
  depuis le registre npm avec des épingles exactes et garde son propre lockfile,
  exactement comme un thème externe. C'est délibéré : il prouve que les paquets
  publiés fonctionnent.
- **Épinglé aux SDK sous revue** : `@wocart/storefront` 1.19.0,
  `@wocart/theme` 2.1.0, Astro 7.3, TypeScript 6.
- **Deux adaptateurs, un seul code de composition** : les builds Cloudflare et
  Vercel ne diffèrent que par l'adaptateur et quelques liaisons de plateforme.
- **Ses propres commandes** : `npm run dev`, `npm test`, `npx astro check`,
  `npm run validate:all`, `npm run build`. Il n'y a pas de script `typecheck` —
  `astro check` est le typecheck.

## Ce qu'il utilise des SDK

| Capacité du SDK | Theme-00 |
| --- | --- |
| `createStoreClient` | `src/theme/sdk.ts` — le seul endroit où un client est construit |
| Config et `contentOverrides` | la même couture passe `theme: THEME_KEY` ; le middleware construit le contexte de requête |
| Composition | `src/theme/pages/*.astro` rendent une surface via `resolveSurfaceDocument` + `InstanceView` |
| Définitions et manifeste | `src/theme/theme.ts` assemble le catalogue ; `src/pages/wocart-theme.json.ts` l'expose |
| Zones | `src/theme/pages/header.area.json`, `footer.area.json` |
| Gabarits et params | les surfaces produit, catégorie, collection et page lisent `Astro.params` |
| Champs de style et schémas | `src/theme/appearance.ts` (tailles) et `src/pages/wocart-styles.css.ts` |
| Réglages | `src/theme/settings.ts` + `src/theme/runtime/settings.ts` |
| Aperçu | `src/pages/wocart-preview.astro` + `@wocart/theme/preview` |
| Revalidation | `src/pages/wocart-revalidate.ts` + `readRevalidateRequest` |
| Routes API same-origin | `src/theme/api-routes.ts` construit sur `createStorefrontRoutes`, exporté en une ligne par `src/pages/api/*` |
| Action de commande | `src/actions/` enveloppe `placeOrderInput` et `executePlaceOrder` |
| Images | `src/theme/utils/images.ts` lie `createImageHelpers(MEDIA_DOMAIN)` ; `src/theme/utils/image-service.ts` lie `mediaImageService` |
| Copie et pluriels | packs `src/theme/content/` + `formatMessage` via `src/theme/content/messages.ts` |

Chacun de ces points est le SDK utilisé comme documenté — c'est ce qui rend le
thème lisible comme exemple.

## Son architecture

```text
src/
├─ middleware.ts              contexte de boutique, langue, passage aperçu/revalidation
├─ actions/                   enveloppe placeOrder
├─ pages/
│  ├─ api/                    exports d'une ligne de src/theme/api-routes.ts
│  ├─ index.astro             surface accueil
│  ├─ products/[handle].astro surface produit (gabarit)
│  ├─ category/[slug].astro   surface catégorie
│  ├─ collections/[handle].astro
│  ├─ pages/[slug].astro      pages de boutique (légales, informatives)
│  ├─ lp/[slug].astro         landing pages
│  ├─ checkout.astro, thank-you.astro, 404.astro
│  ├─ wocart-preview.astro    la route d'aperçu de l'éditeur
│  ├─ wocart-revalidate.ts    vide les pages en cache après une publication
│  ├─ wocart-theme.json.ts    le manifeste, un artefact de build
│  └─ sitemap.xml.ts, robots.txt.ts
└─ theme/
   ├─ sdk.ts                  l'UNIQUE adaptateur SDK
   ├─ theme.ts                le catalogue complet (manifeste + aperçu)
   ├─ catalog/
   │  ├─ families/            un catalogue par surface, importé par sa route
   │  ├─ home/ product/ listing/ header/ footer/   *.def.ts, un par section
   │  ├─ shared.ts            clés de lecture et pont de copie
   │  └─ labels.ts            chaque libellé d'éditeur, en trois langues
   ├─ components/             les composants .astro (sections, layout, ui)
   ├─ runtime/store.ts        le contexte de boutique de la requête
   ├─ runtime/render-context.ts
   ├─ layouts/                StoreLayout et compagnie
   ├─ styles/                 jetons de design et CSS
   ├─ content/                packs ar/ fr/ en/, un fichier par zone, plus messages.ts
   ├─ bridges/                choix de props d'îlots et formes de page-data
   ├─ pages/                  HomeSurface.astro, SurfacePage.astro, *.page.json, *.area.json
   ├─ settings.ts             la déclaration des réglages
   ├─ appearance.ts           les tailles de style et le schéma de page
   ├─ key.ts, version.ts      la clé et la version du thème
   └─ __tests__/              guards/ et contracts/
```

Trois conventions de nommage méritent l'attention, car ce sont elles qui rendent
un grand thème navigable : **un fichier de définition par section**, **un
catalogue par famille de surfaces**, et **un fichier de contenu par zone et par
langue**.

## Ce qui est contrat, et doit être copié

| Règle | Pourquoi elle n'est pas optionnelle |
| --- | --- |
| Un seul module construit un client, et il passe `theme: THEME_KEY` | Sinon les éditions de texte et les documents de page n'arrivent jamais |
| Le document enregistré gagne ; absent, invalide, d'un autre thème ou sans recouvrement, le document livré se rend | Un changement de thème ou un mauvais enregistrement ne doit jamais vider une boutique |
| Un `createReadCache()` par rendu de page | La même lecture de catalogue est partagée par toutes les sections |
| Le contexte de rendu porte `locale` **et** `fallbackLocales` | Une valeur traduite absente pour la langue retombe par valeur |
| Le manifeste est un artefact de build à `/wocart-theme.json` | Un manifeste invalide fait échouer le build au lieu d'être publié |
| Un aperçu n'est jamais mis en cache, et chaque page en cache porte le tag `pages` | Une publication doit atteindre les acheteurs, un brouillon ne doit pas fuir |
| Le thème n'écrit jamais un document, un réglage ou un texte marchand | Les écritures appartiennent à la plateforme, avec son autorisation |
| Les chaînes destinées à l'acheteur vivent dans des packs par langue | Pas de texte codé en dur, pas de langue découverte à l'exécution |
| Chaque lien interne est localisé | Un acheteur français reste en français |

Chacune de ces règles a un test dans Theme-00 — voir la liste des gardes
ci-dessous.

## Ce qui est une décision de Theme-00, pas du SDK

Ce sont de bons choix, et un nouveau thème est libre de choisir autrement :

- **Des catalogues par surface.** `catalog/families/home.ts` déclare un catalogue
  qui ne contient que les sections affichables sur l'accueil, et la route
  d'accueil rend avec lui ; `theme.ts` assemble le catalogue complet pour le
  manifeste et l'éditeur. Les deux sont des `ThemeDefinition` de même `key`.
  L'avantage est une surface de rendu plus petite ; le coût est qu'un document
  enregistré qui référence une section d'une autre famille retombe sur le défaut
  (`no-overlap`). Le motif SDK plus simple est un seul catalogue pour tout.
- **Les composants lisent tout le pack de contenu.** Certains prennent
  `content: StoreFrontContent` et superposent `copyOverrides(content, props)` au
  lieu d'une prop par `contentKey`. Le SDK accepte les deux ; les props par champ
  sont le chemin le plus court.
- **Des clés de lecture constantes** (`catalog.products`, `catalog.categories`,
  `collectionRead(handle, limit)`). Le SDK exige seulement une clé stable dans un
  même rendu.
- **Un design system** (`styles/`, `appearance.ts`, polices, jeu d'icônes). Le
  SDK ne connaît aucun jeton de thème ; les pas de style doivent correspondre à
  *quelque chose*, et les pixels sont ceux du thème.
- **Les îlots serveur et leurs choix de `copy`** (`bridges/island-props.ts`).
  Une optimisation Astro avec une contrainte Astro (les props d'îlot voyagent
  dans une URL), pas une fonction du SDK.
- **Des fichiers de route minces réexportant `src/theme/api-routes.ts`.** Les
  routes elles-mêmes sont celles du SDK (`createStorefrontRoutes`) ; le fichier
  d'une ligne est un détail de routage par fichiers.
- **Ses gardes et validateurs** (`__tests__/guards/`, `scripts/validate-*.js`).
  Puissants, et spécifiques à ses conventions — copiez l'idée, pas les règles.

## Les gardes qui valent la copie

Theme-00 transforme ses frontières en tests qui échouent. Un nouveau thème doit
avoir des équivalents pour au moins ceux-ci :

| Garde | Ce qu'elle fige |
| --- | --- |
| `sdk-boundary.test.ts` | Un seul adaptateur SDK ; pas d'import profond ; pas d'import `cod-shared` |
| `store-context.test.ts` | Un seul endroit construit le contexte de requête ; chaque lien interne passe par le `href` du store |
| `no-validator-in-browser.test.ts` | Pas de Zod dans un script navigateur |
| `page-paths.test.ts`, `page-contracts.test.ts` | Chaque type de page à son chemin de plateforme, avec son script requis |
| `localized-links.test.ts` | Aucun lien interne non localisé |
| `manifest-artifact.test.ts` | Le point d'entrée du manifeste est prérendu et porte toutes les surfaces |
| `preview-route.test.ts`, `revalidate-route.test.ts`, `cache-contracts.test.ts` | En-têtes d'aperçu, tag de cache `pages`, et le crochet de publication |
| `home-editor-sections.test.ts`, `editor-coverage-contracts.test.ts` | Chaque mot rendu est éditable ; pas de copie figée |
| `home-languages-contracts.test.ts`, `packs.test.ts` | Parité des trois langues, et copie enregistrée qui suit la langue de la boutique |
| `sdk-boundary-contracts.test.ts` | Les SDK sont importés uniquement par leurs points d'entrée |

## Comment lire une section dans Theme-00

1. **Trouvez la définition** — `src/theme/catalog/<family>/<type>.def.ts`. La
   chaîne `type` est l'identité de la section ; les champs sont sa surface
   éditable.
2. **Trouvez le composant** — l'import `component:` dans cette définition.
3. **Trouvez l'entrée du document** — `src/theme/pages/<surface>.page.json`, par
   `type` et `id`.
4. **Trouvez son test** — le fichier correspondant sous `__tests__/contracts/`.
5. **Vérifiez ce qui relève du SDK** dans cette documentation avant de supposer
   que le motif se généralise.

## Ce que Theme-00 ne prouve pas

- Ce n'est pas un starter kit. Il n'y a ni générateur ni CLI ; sa structure est
  une convention, pas une API.
- Sa copie, son design, ses polices et sa liste de sections sont les décisions
  produit d'une vitrine.
- Ce n'est pas la suite de tests du SDK. Les tests des paquets dans
  `wocart-sdk/{storefront,theme}/src` définissent le contrat ; Theme-00 le
  consomme.
- Son `AGENTS.md` consigne des décisions et des contournements datés. Certains
  sont historiques ; le code et les `CHANGELOG.md` des paquets disent ce qui est
  actuel.
